# NVIDIA NVENC и denoise — 2026-10-05

**Статус: аппаратная поддержка отложена пользователем 2026-10-05.**
Рекомендации ниже сохраняются как результаты исследования, а не текущий план
внедрения. Программа продолжает использовать CPU-кодировщики SVT-AV1 и x265.

## Вывод

HEVC NVENC на RTX 4070 Laptop GPU даёт существенный выигрыш скорости.
На полном Frantisek с сохранением всех кадров и без удаления снега:

| Режим | Encode wall time, с | Размер, байт |
|---|---:|---:|
| HEVC NVENC CQ28, denoise off | 10,815 | 82 740 844 |
| HEVC NVENC CQ28, medium | 10,817 | 82 089 845 |
| SVT-AV1 CRF48/preset6, medium | 67,823 | 96 038 028 |

NVENC с medium примерно в 6,27 раза быстрее этого CPU-контроля. Включение
HQDN3D изменило время NVENC лишь на 0,018%, размер уменьшился на 0,787%.
Разницы времени в пределах этих измерений нет; это не означает, что CPU-фильтр
бесплатный. Измерялось wall time, не отдельный CPU time/энергопотребление.
Все 10 294 кадра сохранены, каждый PTS совпал с исходным в пределах 1,1 мс,
полный decode выполнен с `-xerror`. AV1 — один полный прогон, NVENC — два,
во втором порядок medium/off обращён; размеры повторов совпали.

Это **не** сравнение равного качества: NVENC CQ28, x265 CRF32 и SVT CRF48
несопоставимы численно. Полный файл содержит белый шум; его кодирование сильно
влияет на размеры. Нельзя сравнивать эту таблицу с прежними 57,9 MB AV1 после
вырезания снега и split. На полезных отрывках NVENC CQ28 давал более крупные
файлы, чем CPU defaults; универсальный победитель по качеству/размеру не определён.

Рекомендация: добавить отдельный ручной вариант **HEVC / H.265 (NVIDIA NVENC)**
с runtime-проверкой доступности; не переключать default автоматически по одному
факту наличия NVIDIA. Это предложение, backend в приложение ещё не добавлен.
CQ для NVENC должен явно отличаться от CRF программных кодировщиков.

## Оборудование и совместимость

Lenovo Legion Pro 5 16IRX9 (83DF), RTX 4070 Laptop GPU, Windows 11 Pro x64.
Активный драйвер 580.97. Рабочий FFmpeg 9.0.2 содержит `hevc_nvenc`, но реальный
encode отказал: required NVENC API 13.1, found 13.0; FFmpeg сообщил minimum
driver 610.00. Наличие GPU и имени encoder в списке недостаточно.

Взята отдельная переносная FFmpeg 7.1.1 Gyan в
`outputs/nvenc-runtime-7.1.1/`, без изменения среды приложения и драйвера.
SHA256 ZIP `d760e1b3574402ed18b4865851f87d87e73965a982e6453212df8621fed1c508`
проверен по [манифесту Microsoft WinGet](https://github.com/microsoft/winget-pkgs/blob/master/manifests/g/Gyan/FFmpeg/7.1.1/Gyan.FFmpeg.installer.yaml).
NVENC и x265 запущены FFmpeg 7.1.1; SVT-AV1 — рабочей 9.0.2.
Старый SVT в 7.1.1 отказал на filter time base lossless-клипа с ошибкой
maximum frame rate 240 fps, поэтому CPU-контроль использует действующий runtime.
Различие версий — ограничение опыта, оно записано в environment JSON.

Повтор после сообщения пользователя об обновлении драйвера пока не удался:
`nvidia-smi` показывает 580.97, Windows SignedDriver — 32.0.15.8097,
FFmpeg 9.0.2 снова сообщил API 13.1/13.0 mismatch. Причина не установлена;
возможен ожидающий перезапуск или установка другого пакета. Свежий драйвер
в активном состоянии не подтверждён, результатов encode на нём нет.

## Одинаковые короткие фрагменты

Использованы lossless FFV1-фрагменты из повторной проверки denoise с 2 с
прогрева; источник/размеры не меняются, звук удалён, deinterlace и snow/split
выключены. Выход limited YUV420, `-fps_mode passthrough -enc_time_base:v filter`.
NVENC: `-preset slow -rc vbr -cq 28`, без дополнительных bitrate/maxrate.
CPU: SVT CRF48/preset6/4 потока, x265 CRF32/**medium**/pools4/frame-threads1.
Во всех парах HQDN3D medium `3:5:1.5:6` или off.

| Фрагмент | NVENC off, с | NVENC medium, с | Экономия размера от medium |
|---|---:|---:|---:|
| home 95–106, слабый сигнал | 1,040 | 0,991 | 0,096% |
| home 120–124, коробка | 0,490 | 0,476 | 0,254% |
| stadion 18–26, движение | 0,583 | 0,574 | 0,748% |
| Frantisek 8–14, переворот | 0,521 | 0,524 | 1,375% |

Два повтора NVENC, один CPU; на коротких сценах запуск процесса/контекста
занимает значительную часть времени. Малые отрицательные изменения не доказывают
ускорение фильтром. Все кадры и timestamps проверены, все outputs декодированы.

| Фрагмент | NVENC medium: MB / с | SVT medium: MB / с | x265 medium: MB / с |
|---|---:|---:|---:|
| Слабый сигнал | 2,007 / 0,991 | 3,160 / 2,413 | 1,025 / 3,167 |
| Коробка | 0,431 / 0,476 | 0,048 / 0,699 | 0,028 / 0,562 |
| Стадион | 1,557 / 0,574 | 1,049 / 1,845 | 0,477 / 2,110 |
| Frantisek motion | 1,060 / 0,524 | 0,502 / 1,229 | 0,239 / 1,306 |

Дополнительный NVENC CQ36/off на motion: 383 535 байт, 2,187 с, 180 кадров;
одиночный запуск после простоя не годится для вывода о времени. Параметр CQ
сильно меняет результат; подбор равного размера/субъективного качества не завершён.

## Точная команда товарища

```powershell
ffmpeg -hwaccel cuda -i Frantisek.AVI -c:v hevc_nvenc -preset slow -rc vbr -cq 28 -an output.mkv
```

На нашей GPU/FFmpeg 7.1.1: 10,930 с, 87 949 949 байт, 10 294 кадра,
максимальная ошибка исходного PTS 0,5 мс, полный decode прошёл. Результат
товарища 19 с / около 134 MB — внешнее измерение, его железо/FFmpeg неизвестны.
Параметры кодирования одинаковые, но окружение не установлено как одинаковое.
Время полного CUDA-варианта близко к CPU decode + NVENC; утверждать выигрыш
CUDA decode из этого одиночного прогона нельзя.

## OSD и смысл опции

Созданы совпадающие кадры source/SVT/x265/NVENC с увеличенными цифрами OSD.
На выбранных кадрах NVENC CQ28 выглядит близко к исходному по цифрам; это
покадровая проверка, не полноценная оценка читаемости во времени. Для motion
NVENC-файл более чем вдвое больше SVT: не приписывать различие качества только
аппаратуре. Приёмку OSD нужно проводить на нескольких моментах и при сопоставимом
размере либо выбранном пользователем уровне детализации.

Для автоопределения предложен короткий настоящий encode с таймаутом через
выбранный FFmpeg, кэшируемый на запуск приложения. Проверять codec backend
в ядре и повторять перед заданием при изменении пути FFmpeg. Показать доступность
и причину отказа. Не ставить драйвер автоматически и не скрывать замену ручного
NVENC на CPU. HQDN3D остаётся на CPU; CUDA decode — отдельная возможность,
не обязательная часть NVENC. NVIDIA описывает варианты software decode/hardware
encode в [официальном руководстве](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.0/ffmpeg-with-nvidia-gpu/index.html).

## Материалы

### Дополнительная проверка альтернатив Windows

В том же ноутбуке Windows видит Intel UHD Graphics, драйвер 31.0.101.5187,
помимо NVIDIA. В рабочем FFmpeg 9.0.2 присутствуют `hevc_qsv`, `hevc_amf`
и `hevc_nvenc` (также H.264/AV1 варианты). Двухкадровая проба 640×480/NV12
с таймаутом 15 с: **Intel HEVC QSV прошла**, 0,521 с; AMD AMF отказал за
0,032 с, отсутствует `amfrt64.dll` (AMD GPU в системе нет). NVIDIA уже проверена
и недоступна с этой сборкой из-за driver/API mismatch. Это тест доступности,
не измерение QSV на DVR, качества или скорости длинного файла.
Доказательства: `outputs/hardware-backend-probes-2026-10-05.json`.

Значит, практическое обнаружение нескольких backends возможно без установки
дополнительных SDK: список encoders в выбранной сборке, затем короткая проба
каждого кандидата с таймаутом. Поддержка HEVC не доказывает поддержку AV1;
проверять отдельно каждый codec/backend и используемые форматы пикселей.
Универсального процента совместимости без выборки компьютеров нет. Нужен
проверенный комплектный runtime, ясное сообщение об отказе и CPU fallback.

`benchmarks/recheck_nvenc.py --directory outputs/nvenc-new --ffmpeg-dir outputs/nvenc-runtime-7.1.1`.
Требуются prepared clips из `benchmarks/recheck_denoise.py`; новая папка результата.
`outputs/nvenc-final-2026-10-05/`: environment, runs/summary, команды/логи,
полные и короткие MKV, `*-osd-comparison.png`, `cq36.json`.
Первые отказы сохранены в `outputs/nvenc-recheck-2026-10-05/` и
`outputs/nvenc-compatible-2026-10-05/`; повтор после обновления —
`outputs/nvenc-new-driver-2026-10-05/`. Материалы локальные, Git их игнорирует.
Исходные AVI и существующие результаты пользователя не изменялись.
