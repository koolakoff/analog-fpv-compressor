# Временная шкала и чересстрочность DVR: 2026-10-04

## Что проверено

Оба локальных AVI целиком прочитаны ffprobe по пакетам, декодированы FFmpeg
с `-xerror` (видео и аудио), затем декодированы в `framemd5` для поиска
побитово одинаковых соседних изображений. Для idet взято по пять выборок
с запросом 400 выходных кадров вне размеченного пользователем белого шума.
FFmpeg — локальная сборка 9.0.2. AVI не изменялись.

Воспроизводимый инструмент: [analyze_timing.py](../../benchmarks/analyze_timing.py).
Пример запуска из корня проекта:

```powershell
.\.venv\Scripts\python.exe benchmarks/analyze_timing.py --ffmpeg-bin 'C:\Users\user\AppData\Local\Microsoft\WinGet\Packages\Gyan.FFmpeg_Microsoft.Winget.Source_8wekyb3d8bbwe\ffmpeg-9.0.2-full_build\bin'
```

Сырые данные находятся локально в `benchmarks/results/timing/`: паспорта,
пакеты, framemd5, idet и stderr, точные команды с кодами возврата и временем,
сводные JSON. Каталог исключён из Git. Этот документ содержит проверяемые
числа и выводы, не копию исходного видео.

Оба потока начинаются с PTS=0. Аудио PCM 8000 Hz имеет непрерывную временную
шкалу; его конечная длительность практически совпадает с видео. Это проверка
контейнера, не доказательство физической синхронизации камеры и микрофона.

`nb_frames` в этих файлах нельзя использовать как число реально доступных
изображений. Одного индекса декодированного кадра также недостаточно для
таймкода: необходим его фактический PTS.

В oneflight пять интервалов равны двум слотам и один — трём. Последний начинается
на 279.198920 с, перед указанным пользователем началом снега около 280 с.
Другие разрывы начинаются на 0.033397, 83.793073, 281.302931, 284.074882
и 284.375455 с. Приблизительную пользовательскую разметку это не уточняет
автоматически: нужен просмотр перехода.

В with-termination разрывы сильно сосредоточены на размеченном участке снега:

| Участок исходной шкалы | Число разрывов | Отсутствующие слоты |
|---|---:|---:|
| До 76 с | 2 | 6 |
| 76–144 с | 146 | 431 |
| После 144 с | 4 | 6 |

Самый большой промежуток — от 94.827792 до 95.841806 с. Следующие крупные:
133.430256–134.409304 и 129.863724–130.772840 с. Разметка по границам
использует соседние PTS; это группировка для исследования, не детектор снега.

Связь разрывов с потерей сигнала подтверждается их распределением. Но это
не доказывает, что именно потеря сигнала объясняет разницу **базового шага**
двух AVI. Реальная частота камеры, алгоритм расчёта заголовка DVR и место
возникновения отсутствующих изображений пока неизвестны. Разные значения
заголовка не доказывают разные режимы камеры; исправлять их на 30 fps
без дополнительного основания нельзя.

## Чересстрочность

Выборки oneflight начинаются на 10, 24, 60, 150 и 260 с;
with-termination — на 10, 50, 150, 230 и 310 с.
Из-за внутреннего буфера idet его счётчики содержат 401 анализированный
кадр на выборку при запросе 400 выходных кадров.

Multi-frame idet для oneflight: 2005 progressive, 0 TFF/BFF, 0 undetermined.
Для with-termination: 2004 progressive, 0 TFF/BFF, 1 undetermined.
Single-frame показывает лишь 3 TFF/BFF-кандидата на первую запись и
3 BFF-кандидата на вторую. Устойчивое чересстрочное содержимое в выборках
не обнаружено. Для текущего baseline этих записей обоснован `deinterlace=off`;
удваивать FPS через bwdif не требуется. Это не универсальный default для
других DVR и не утверждение о всех невыбранных кадрах.

## Следствия для обработки

- Сохранять исходные временные метки и промежутки между изображениями;
  для кодирования исследовать `-fps_mode passthrough`/VFR.
- Не использовать `setpts=N/fps` и не назначать таймкоды как `index/header_fps`:
  это сокращает запись на промежутки без изображения, особенно во второй AVI.
- Для вырезания использовать границы исходного времени; `trim`/`atrim`
  с одинаковыми границами сохраняют внутренние разрывы шкалы. В текущем
  video-only исследовании сегмент сбрасывается через `PTS-STARTPTS`; при
  `audio=keep` обоим потокам нужен общий сдвиг относительно исходной границы,
  чтобы разные первые samples/frames не потеряли взаимное смещение.
- При `audio=keep` отсутствие нового видеокадра не означает необходимость
  удалить соответствующее аудио. Проверять начало/конец обоих потоков после
  кодирования и concat; реальные звуковые/визуальные события требуют отдельной
  проверки синхронизации.
- Отсутствие точных соседних MD5-повторов не исключает повторяемую сцену:
  новый шум или изменения JPEG могут менять пиксели. Пропущенное изображение
  этим тестом восстановить или распознать нельзя.

Настройка range должна отдельно учитывать полный диапазон MJPEG
`yuvj422p`, отмеченный ffprobe. Этот анализ не оценивает корректность
преобразования диапазона или полезность сжатого изображения.
