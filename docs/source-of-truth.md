# Источник истины: analog-fpv-compressor

## Смысл и цель проекта

**analog-fpv-compressor** — программа для сжатия DVR-записей с аналоговых
FPV-дронов. Цель — максимально уменьшить размер видеофайла за счёт фильтрации
помех, вырезания участков полного белого шума и оптимизации обработки
и кодирования видео.

При сжатии важно сохранять полезную информацию о полёте: движение дрона,
геометрию сцены и видимые препятствия, в том числе кратковременно появляющиеся
в кадре. Точная передача мелких текстур и самих помех вторична.

[«Сжатие аналогового FPV видео»](https://chatgpt.com/c/6ac13181-c674-83ed-a991-43ee7c4b164e).

### Локализация GUI

Требование четырёх языков задано пользователем 2026-10-04.
Предлагаемые правила реализации:

- Английский — базовый язык и fallback для отсутствующего перевода.
  При первом запуске использовать язык системы, если он поддерживается;
  предоставить явный выбор и сохранять его для следующих запусков.
- Переводить подписи, меню, подсказки, проверки ввода, состояния задания
  и пользовательские сообщения об ошибках. Не собирать предложения из
  отдельных переведённых слов; использовать шаблоны с параметрами и формы множественного числа.
- Переводы хранить отдельно от обработки. Для предложенного PySide6 использовать
  штатные Qt translation catalogs и QTranslator; новые языки подключаются
  через каталог переводов. Это рекомендация, не окончательный выбор GUI framework.
- Желательно переключать язык без перезапуска приложения и без прерывания
  выполняющегося задания. Проверять длину подписей, кириллицу и диакритику
  на всех четырёх языках; элементы не должны обрезать текст перевода.
- Машинные события содержат стабильный код сообщения и отдельные параметры,
  которые GUI отображает на выбранном языке. CLI-опции, ключи JSON,
  значения enum и численные данные машинного протокола не переводятся.
  Исходные диагностические сообщения FFmpeg сохраняются как получены.
- По решению пользователя консольный вывод всегда на английском: help,
  подсказки, статусы, предупреждения, ошибки и итоговые сообщения, независимо
  от языка ОС или GUI. GUI переводит собственные сообщения из событий;
  сырой диагностический лог остаётся в исходном виде. Язык отдельных файловых
  логов и отчётов пока остаётся рабочим предложением — английский.
- GUI может отображать числа по локали; CLI/машинный контракт использует единый
  формат, например десятичную точку. Язык интерфейса не меняет фактические настройки.

Механизм Qt: [перевод приложений](https://doc.qt.io/qtforpython-6/tutorials/basictutorial/translations.html).

### Предлагаемый контракт параметров

Значения `auto` выражают политику программы: выбор на основе свойств файла
и откалиброванных defaults. Они не обещают математически оптимальный размер
и не требуют дорогого поиска параметров для каждого входа. В отчёте показывать
как запрошенные настройки, так и фактически выбранные значения с причиной.
Версию политики/defaults сохранять, чтобы результат можно было повторить.

| Настройка | CLI, предложение | GUI, предложение | Семантика |
|---|---|---|---|
| Входной файл | `--input PATH` | Выбор файла / поле пути | Обязательный путь к одному DVR-файлу; без auto. До обработки проверить существование, доступность и наличие поддерживаемого видеопотока. |
| Аудио | `--audio remove\|keep` | «Сохранять звук», по умолчанию выключено | Default — `remove`: результат без аудиопотока. `keep` сохраняет звук, если он есть, с синхронным вырезанием тех же интервалов. |
| Качество кодирования | `--crf auto\|N` | Авто / численное качество | Исходный auto режим использует откалиброванный CRF; размер заранее не фиксирован. |
| Видеобитрейт | `--bitrate auto\|VALUE` | Авто / целевой битрейт с единицами | Auto оставляет выбор режима программе. Ручное значение задаёт целевой средний видеобитрейт, а не точный размер всего файла. |
| Разрешение | `--scale auto\|original\|WIDTHxHEIGHT` | Авто / исходное / выбранный размер | Auto использует проверенную политику downscale, сохраняя понятность сцены; без обоснования сохраняет исходное. |
| Шумоподавление | `--denoise auto\|off\|weak\|medium\|strong` | Авто / выключено / степень | Уровни отображаются в откалиброванные HQDN3D-параметры; окончательное число уровней выбрать после benchmark. |
| Deinterlace | `--deinterlace auto\|off\|on` | Авто / выключено / включено | Auto следует результату idet; on принудительно включает bwdif. |
| Порядок полей | `--field-order auto\|tff\|bff` | Расширенная настройка | Используется при deinterlace; позволяет исправить неверные флаги DVR. |
| Вырезание снега | `--cut-no-signal auto\|off` | Авто / выключено | Auto удаляет только подтверждённые интервалы; off сохраняет временную шкалу. |
| Минимальная длительность снега | `--no-signal-min-duration auto\|SECONDS` | Авто / длительность в секундах | Положительная минимальная длительность кандидата до подтверждения; не заменяет признаки, гистерезис и запас вокруг границ. |
| Скорость кодирования | `--preset auto\|N\|NAME` | Авто / скорость кодирования | Компромисс время/размер: численный preset для AV1, именованный для HEVC. |
| Кодек | `--codec av1\|hevc` | Расширенная настройка | Default AV1; HEVC доступен для ручного сравнения. |

Памятка перед добавлением мультифайла: пересмотреть контракт входа, назначения
результатов и логов в CLI/GUI. Определить представление списка файлов, порядок
при склейке, выбор режима (независимая обработка или склейка), применение настроек
ко всему заданию/отдельным файлам и именование результатов. Сохранить совместимость
с запуском для одного файла либо явно описать миграцию. Сейчас `--input` принимает
ровно один файл; список и новые режимы пока не реализуются.

Для аудио `auto` не требуется: default явно задан как `remove`.
При `remove` исключать аудиопотоки и не выполнять ненужную обработку звука.
При `keep` сохранять синхронизацию с видео, включая исходное смещение потоков
и склейку после вырезания no-signal. Если звука во входе нет, это не ошибка:
создать видео без звука и указать это в логе. `keep` не означает обязательное
побитовое копирование: при необходимости обработки допускается перекодирование;
Текущий выбор: FLAC для MKV, AAC для MP4; подробности ниже в контракте ядра.

CRF и целевой битрейт — разные способы управления кодированием. Если пользователь
явно задал оба, сообщить конфликт до запуска, а не молча игнорировать один.
Ручной bitrate при `crf=auto` выбирает bitrate-режим; ручной CRF при `bitrate=auto`
выбирает CRF-режим. При обоих auto исходная политика — CRF.
Поддержку этих режимов подтверждать для выбранного encoder/сборки.
Основание: [параметры кодировщиков FFmpeg](https://ffmpeg.org/ffmpeg-codecs.html#libsvtav1).

`denoise=off` полностью исключает HQDN3D из filtergraph и не запускает
отдельный анализ силы denoise. Это не выключает кодировщик или его внутренние
механизмы. `deinterlace=off/on` не требует idet ради auto-решения.
`cut-no-signal=off` не запускает поиск интервалов ради вырезания; если выборки
полезного сигнала нужны другому включённому auto-этапу, назначение анализа должно
быть явным. Отключённые этапы не должны выполнять лишнюю работу.

Downscale сохраняет отображаемые пропорции с учётом SAR/DAR, не увеличивает
разрешение автоматически и не обрезает изображение скрыто. Несовместимый ручной
размер объясняется или отклоняется. Auto не может надёжно узнать фактическую
детализацию камеры только по размеру DVR: пока политика не проверена, не
выбирать единое уменьшение для всех источников.

### Предлагаемый пользовательский сценарий

CLI: входной файл и путь результата, необязательные настройки,
`--help` с единицами/диапазонами, режим анализа без encode, понятные ошибки
и итоговый отчёт. Предусмотреть ненулевой код завершения при ошибке.

GUI: выбор входа и назначения, основные настройки, раскрываемая группа
расширенных параметров, запуск/отмена, текущий этап и прогресс, итоговый размер
и время, возможность открыть результат и отчёт. При auto показывать выбранные
значения после анализа. Не требовать знакомства с FFmpeg для обычного запуска.
Во время обработки интерфейс остаётся отзывчивым.

Процент и ETA показывать только когда их можно оценить; предварительный анализ
и encode имеют разные длительности. Не обозначать запуск процесса как завершение
задачи. Параметры не менять посреди задания; для следующего запуска — можно.

### Логирование и отчёт о решениях

UI5 добавлено по запросу пользователя 2026-10-04. Предлагаемые правила:

- Читаемый лог CLI выводить в stderr; stdout оставить для явно включённого
  машинного вывода. В GUI показывать те же сообщения через панель лога.
- По умолчанию сохранять отдельный UTF-8 лог задания рядом с результатом;
  предусмотреть `--log-file PATH` и настройку назначения в GUI. Не затирать
  лог другого задания. До запуска проверять доступность каталога записи.
- Фиксировать время события, этап и уровень `INFO/WARNING/ERROR`;
  подробный `DEBUG` включать отдельно. Подавлять избыточное повторение
  прогресса в файловом логе, не скрывая решений и ошибок.
- В начале записывать вход/назначение, версии инструментов и запрошенные
  параметры. После анализа — фактические CRF/bitrate, размер, denoise,
  deinterlace/field order, preset, audio и no-signal настройки: что выбрал пользователь,
  что решил auto и почему. Записывать также выключенные или пропущенные этапы.
- Для каждого удалённого интервала приводить начало, конец и длительность
  **на временной шкале исходного файла**, например `00:03:14.200–00:04:01.500`.
  Это окончательные границы удаления после применения сохраняемого запаса,
  а не только грубые границы кандидата детектора. Семантика интервалов —
  `[start, end)`. Отдельно суммировать удалённое время и число интервалов.
- При ошибке/отмене указывать этап, причину и состояние output; при успехе —
  исходную/выходную длительность и размер, время обработки и расположение результата.
  Ошибка не должна заканчиваться сообщением об успешном завершении.

Лог объясняет выполнение человеку. Машинные события служат GUI, а итоговый
структурированный отчёт хранит настройки и mapping для повторения и анализа;
все три представления формируются из одних данных задания. Полный stderr
FFmpeg можно сохранять в подробном диагностическом режиме отдельно от основных
сообщений, чтобы не затруднять чтение принятых решений.

| T7 | Отчёт хранит настройки, их фактические значения, версии инструментов/политики, интервалы, длительность, размер, время и предупреждения. Консольный и файловый логи используют те же данные. | Проверка auto-решений и повторение измерений. |
| T8 | Консольный вывод и тексты в исходниках — на английском. Комментарии, docstrings, описания функций/классов/модулей и базовые сообщения программы пишутся по-английски. | Явное решение пользователя 2026-10-04; единый язык кода и CLI. |

Общение и проектные Markdown-документы могут оставаться на русском.
Переводы GUI на ru/uk/sk хранятся в отдельных каталогах локализации;
они не нарушают правило английского языка исходников. Базовые UI-строки
и идентификаторы в коде — английские. Пользовательские пути и содержимое
входных данных сохраняются в исходном виде, а не переводятся.

Передача аргументов списком и запуск без shell поддерживаются
[subprocess Python](https://docs.python.org/3/library/subprocess.html#frequently-used-arguments);
это рекомендация для текущего прототипа, не выбор языка конечного продукта.
Для воспроизводимости фиксировать ручной план, а не только повторять `auto`.
Не обещать одинаковые байты на разных версиях encoder или оборудования.

Предлагаемая граница слоёв:

```text
GUI → общий Python-пакет / события задания → FFmpeg/ffprobe
CLI → тот же Python-пакет
```

## Будущие возможности

Зафиксированы пользователем 2026-10-04; не входят в первоначальную реализацию:

- Обработка нескольких файлов. Отдельно рассматривать пакет независимых заданий
  и склейку частей одной записи: это разные операции.
- Склейка последовательных DVR-файлов одного полёта, разбитых рекордером
  по лимиту времени/размера. Порядок, совместимость потоков, возможные разрывы
  и дубли кадров нужно проверять; простой concat не всегда достаточен.
- Разделение одной записи на файлы отдельных полётов по длительным no-signal
  паузам при замене батареи. Полный снег — кандидат на границу, но может
  означать и потерю сигнала внутри полёта; минимальную длительность границы
  полёта и политику подтверждения задавать отдельно от порога обычного вырезания.

В первой реализации — один входной файл и один результат. Для будущего расширения
хранить интервалы исходной шкалы отдельно от выходного mapping; сложную систему
batch/склейки/сегментации заранее не реализовывать.

## Финальная рабочая структура

Pipeline основан на S5. Интерфейсы и общий контроллер уточнены в текущем проекте;
реализован Python-пакет в `src/analog_fpv_compressor`.

```text
DVR file → ffprobe → быстрый анализ всего файла
                         ├─ NoSignalDetector → интервалы удаления/сохранения
                         └─ полезные участки → короткие выборки idet
                                               → progressive / TFF / BFF / unknown

План обработки → один финальный проход кодирования:
no-signal cut → условный bwdif → HQDN3D → опциональный scale → SVT-AV1 → файл
```

Один финальный encode допускает предварительные анализ и выборки `idet`.
Промежуточный несжатый видеофайл на диске не требуется.
Crop мусорных краёв обсуждался как условная оптимизация, но не является
обязательным автоматическим этапом последней схемы.

| Логический компонент | Ответственность | Исполнитель |
|---|---|---|
| Probe | Метаданные и свойства входа | ffprobe + обвязка |
| NoSignalDetector | Метрики кадров → автомат состояний → интервалы | Собственный небольшой модуль |
| Interlace analysis | Выбор полезных фрагментов и интерпретация idet | Обвязка FFmpeg |
| Pipeline controller | Probe → анализ → сборка команды → encode | Собственный код |
| Video processing | Decode, deinterlace, denoise, scale, motion estimation, encode, контейнер | FFmpeg/SVT-AV1 |
| Benchmark и отчёт | Сравнение размера, времени и полезности изображения | Отдельный исследовательский инструмент |

Собственный denoiser, decoder, scaler, motion estimator или encoder не пишем.
Python + NumPy используются в ядре; упаковка остаётся отдельным решением.
CLI `fpv-compress.exe input.avi output.mp4` из архива был иллюстрацией;
рабочий контракт параметров приведён в разделе интерфейса выше.

## Решения и обоснования

### D1. Один внешний denoiser — HQDN3D

S3–S5: случайный шум усложняет межкадровое предсказание, поэтому denoise может
облегчить сжатие. HQDN3D уже есть в FFmpeg, прост в интеграции и имеет отдельные
spatial/temporal силы для luma/chroma. Начинаем с OFF/ON и измеряем пользу.
Каскад denoisers увеличивает CPU cost, сложность и вероятность потери короткого
реального события при убывающем дополнительном выигрыше.

Исправление из S4: HQDN3D не отслеживает траву motion vectors. Он фильтрует
пространственно и во времени; motion estimation делает кодировщик.

### D2. Осторожный temporal luma, более сильное chroma

S4: яркостный контур ветки важнее цветной аналоговой ряби. Гипотеза настройки:
умеренный spatial luma, слабый temporal luma, более сильные spatial/temporal chroma.
Численные силы не выбраны. Проверять короткие препятствия обязательно:
это направление эксперимента, а не гарантия сохранения каждой ветки.

### D3. HQDN3D и SVT-AV1 дополняют друг друга

HQDN3D выдаёт обработанные кадры и не заменяет codec. SVT-AV1 — исходный
кандидат на encoder благодаря предсказанию и motion compensation. Это внешняя
библиотека, доступная через FFmpeg `-c:v libsvtav1`; отдельный SvtAv1EncApp не нужен
при подходящей сборке FFmpeg. Сравнение с x265 должно проверить компромисс
размер/время. Наличие второго encoder в конечном продукте ещё не решено.

### D4. Film grain выключен; temporal filtering на defaults

S3–S5: синтетическое восстановление шума противоречит цели пользователя.
Рабочие параметры: `film-grain=0`, `film-grain-denoise=0`.
Внутреннее temporal filtering опорных кадров SVT не равно внешнему denoiser.
`enable-tf`, `tf-strength`, `enable-kf-tf` оставляем на defaults конкретной версии;
численные defaults из чата не переносим слепо. Если исчезают препятствия,
отдельно сравниваем TF ON/OFF. Тезис о меньшем риске TF требует проверки на видео.

### D5. Auto deinterlace на полезных участках

Цифровой файл может сохранять чересстрочные поля; оцифровка не означает progressive.
S5 заменяет настройку под один DVR автоматической проверкой разных источников.
Progressive не обрабатываем bwdif. `idet` анализирует несколько нормальных
участков после no-signal поиска: первые секунды могут содержать только снег.
Предложено 3–5 выборок, суммарно 300–500 полезных кадров. Порог уверенности,
fallback для undetermined и ручное переопределение ещё нужно спроектировать.

### D6. Для interlaced — send_field вместо раннего send_frame

S5: сохраняем временную информацию полей ради кратковременных препятствий.
Рабочий выбор — `bwdif=mode=send_field`; PAL 25i может стать 50p,
NTSC — примерно 59.94/60p в зависимости от источника.
25/30p — отдельный эксперимент компактного режима, не основной auto выбор.
FPS progressive также не снижаем вслепую.

### D7. Полный снег вырезать вместо freeze/reconstruction

S5: пауза с отключённой батареей не содержит полезной картинки, зато плохо
сжимается. Вырезание уменьшает длительность и исключает кадры из denoise/encode.
Ранняя идея подставлять предыдущий хороший кадр заменена. Сохранение исходной
длительности не требовалось; выходная временная шкала меняется.
Сильные помехи с различимой сценой не равны полному отсутствию сигнала.
При сомнении участок сохраняем. Сохранённые участки склеиваются по времени;
запас вокруг переходов не входит в удаляемую часть.

### D8. Небольшой классификатор с длительностью и гистерезисом

S5: сочетать межкадровую разницу, корреляцию и крупную структуру. Для снега
ожидаются высокая разница, низкая корреляция и слабая структура после усреднения.
Одна лишь большая разница может означать быстрый разворот, а не no-signal.
Одиночные странные кадры не удалять. Подтверждение, гистерезис и сохраняемый запас
вокруг границ должны защищать начало и конец полезного участка.

Экспериментальные точки старта: grayscale 128×96 при 5–10 fps, структура на 16×12,
подтверждение 0.5–1 с, запас 0.2–0.5 с. Это не утверждённые пороги.
`signalstats`, `entropy`, `bitplanenoise` были возможными источниками признаков,
не обязательной цепочкой. Возможное влияние OSD и разных DVR нужно исследовать.

### D9. Узкий benchmark отдельно от production

Финальная программа S5: эффективность no-signal cut, HQDN3D OFF/ON,
SVT-AV1 vs x265, при interlaced — 25/30p vs сохранение 50/60 полей в секунду.
NLMeans исключён даже из обязательного первого benchmark. После сравнения
невыгодные варианты не включаются в конечную программу.

Критерии: размер/битрейт, время/скорость и ресурсы, читаемость движения,
геометрии и кратковременных препятствий. VMAF/PSNR против шумного исходника
не основной критерий: удаление ненужного шума может оцениваться как потеря.
Одинаковый CRF у разных codecs не означает одинакового качества.

### D10. Preset около 6; ограниченное сравнение 4/6/8

S4 заменяет ранний старт preset 2/4 выбором около 6 ради баланса скорости
и размера; S5 его не отменяет. Сравнить только 4/6/8, выбрать по измерениям.
Окончательные CRF и preset не заданы. Для 8-bit DVR предложен `yuv420p`
без автоматического перехода на 10-bit. Это экспериментальные исходные решения.

### D11. Crop и downscale только при полезном выигрыше

S3–S4: шумная кромка может расходовать биты, а номинальное разрешение DVR
не обязательно равно полезной детализации аналога. Уточнение пользователя:
допустимы снижение битрейта и downscale, чтобы не сохранять избыточное разрешение
записи относительно фактической детализации аналоговой камеры. Оценивать
результат по понятности движения, объектам и тонким препятствиям. Единого
разрешения для всех камер/DVR заранее не задаём. Проверять crop можно при
подтверждённой пользе. 640×480 и высота около 480 — примеры,
не обязательные размеры. OSD упомянут как полезная информация, если его нужно
сохранять; окончательная политика ещё не определена.

## Исследованные альтернативы и итоговый статус

### Уточнение по измерениям временной шкалы

Исследование 2026-10-04 обнаружило в локальных AVI промежутки между реальными
видеокадрами, не отражаемые простым счётом декодированных изображений.
Сохранять PTS и длительность полезных участков; не нормализовать FPS и не
использовать `setpts=N/fps` автоматически. Для анализа таймкоды брать из
фактических временных меток. Данные и ограничения — в
[исследовании времени](research/timing-2026-10-04.md), результаты benchmark —
в [журнале](research/experiments-2026-10-04.md). Отсутствие interlace в выборках
этих записей не отменяет auto-проверку других DVR.

При сохранении аудио применять общий сдвиг времени по началу исходного
интервала с учётом смещения потоков. Независимый сброс каждого потока к первому
sample/frame может изменить относительное смещение; проверить при реализации.

### Дополнительное исследование: мигания и крупные артефакты

Наблюдение пользователя 2026-10-04: в DVR-записях встречаются мигания всего кадра
или отдельных областей с крупными артефактами. Ошибки синхронизации/передачи —
возможное объяснение, но причина пока не установлена и не выводится только
из внешнего вида записанного видео.

При анализе выделять эти случаи отдельно от полного no-signal, обычного снега,
реальных изменений освещения и быстрого движения камеры. Зафиксировать таймкоды,
длительность, затронутую область и сохранность полезного изображения.
Короткие события проверять на исходной частоте кадров/полей: выборка 5–10 fps
для длительного снега может их пропустить. Низкочастотная выборка не является
достаточной проверкой отсутствия миганий.

Исследовательские гипотезы, не выбранные этапы production:

- Сравнить яркостные/цветовые скачки и структурные изменения по всему кадру
  и крупным областям, включая соседние кадры. Проверить реальные повороты,
  переход свет/тень и препятствия как отрицательные примеры.
- Если меняется в основном яркость, оценить коррекцию или штатный
  [FFmpeg deflicker](https://ffmpeg.org/ffmpeg-filters.html#deflicker).
  Этот фильтр не считать универсальным исправлением повреждённых строк,
  смещения изображения или потери структуры.
- Если кадр/область повреждён, сначала измерить эффект обычного HQDN3D.
  Локальную замену или восстановление по соседним кадрам рассматривать только
  отдельным экспериментом: это может скрыть препятствие, изменить движение
  или создать отсутствовавшие в исходнике детали.
- Не вырезать короткое мигание автоматически как паузу между полётами.
  Если полезная сцена сохраняется, приоритет — сохранить момент и движение.

Сравнивать отсутствие специальной обработки, baseline HQDN3D и максимум
небольшое число подходящих вариантов после классификации дефекта.
Фиксировать размер, время, изменение полезности изображения и риск ложных
срабатываний. Добавлять модуль только при существенной пользе для сжатия
и приемлемой сложности; косметическое устранение миганий само по себе не цель.
В исследовании 2026-10-04 в with-termination около 152 с просмотрены вспышка
и вертикальное смещение частей изображения, а в oneflight около 188.6 с —
резкое реальное движение, создающее сильный temporal-выброс. Наблюдения и
ограничения — в [журнале](research/experiments-2026-10-04.md).
Аппаратная причина помех не установлена.

Уточнение по поиску первичных источников 2026-10-04 (рекомендации для
экспериментов, не утверждение о содержимом наших AVI):

- HQDN3D уже содержит spatial и temporal denoise. Новый temporal-модуль
  не нужен только потому, что дефект меняется во времени. Сильный скачок
  или повреждённая геометрия не равнозначны мелкому шуму; увеличение temporal
  strength может смазывать движение, не исправляя причину.
- Различать мелкий снег/цветовой шум, яркостные/цветовые вспышки, полосы,
  смещение/разрыв строк и прокрутку изображения, полный no-signal.
  Последствия отражений, помех питания, работы приёмника и синхронизации могут
  сочетаться; внешний вид DVR не позволяет однозначно установить причину.
- Простой детектор исследовать только как поиск кандидатов: короткий выброс
  между соседними кадрами, пространственная форма дефекта и сохранность
  структуры после нормализации яркости. Возврат к прежнему виду сам по себе
  не доказательство: настоящий блик, тень и краткое препятствие тоже могут
  появиться на один кадр. При сомнении сохранять исходное событие.
- FFmpeg deflicker корректирует общую яркость по временному окну, не распознаёт
  причину изменения и не восстанавливает повреждённую область. Применение
  ко всей записи без проверки может менять реальные переходы освещения.
  Проверять только как узкий эксперимент для подходящего типа дефекта.
- Восстановление полос/областей при быстром FPV-движении может потребовать
  учёта движения, масок и обработки перекрытий. Это существенно сложнее
  базового pipeline; пока не включать в обязательную V1.
- Гипотеза пользы: удаление непредсказуемых помех может уменьшить затраты
  кодирования. Редкое заметное мигание может дать малый вклад в общий размер;
  простая смена яркости не обязательно дорого кодируется. Проценты не обещать.
  При фиксированном целевом битрейте ожидать прежде всего перераспределения
  качества, а не существенного уменьшения размера при той же длительности.

Рекомендуемый предел исследования: несколько размеченных событий и контрольных
сцен с солнцем, тенями и быстрыми препятствиями; baseline и один подходящий
простой вариант. Сравнить при одинаковых codec/CRF/preset/FPS/scale,
затем проверить, сохраняется ли выигрыш при сопоставимой понятности движения.
Оценить размер всей записи, а не только дефектного фрагмента, и дополнительное
время. Если пользы сверх HQDN3D мало либо нужна сложная реконструкция,
остановить эту ветку и отложить её. Универсальное устранение миганий не
становится условием готовности V1.

Первичные источники (проверены 2026-10-04):

- [FFmpeg: HQDN3D](https://ffmpeg.org/ffmpeg-filters.html#hqdn3d)
  — пространственные и временные параметры.
- [FFmpeg: исходник deflicker](https://ffmpeg.org/doxygen/trunk/vf__deflicker_8c_source.html)
  — коэффициент коррекции из яркости кадров; классификации помех нет.
- [ImmersionRC rapidFIRE, руководство Rev 1.4, копия PDF](https://m.media-amazon.com/images/I/B1448syfrzL.pdf)
  — multipath, реконструкция в приёмнике, режим Sync Lock и rolling.
  Работа с двумя сигналами до DVR не эквивалентна фильтрации одного AVI.
- [Analog Devices: CVBS и восстановление DC-уровня](https://www.analog.com/en/resources/app-notes/an-1603.html)
  — совместная передача яркости, цвета и синхронизации, связь уровня с яркостью.
- [Analog Devices: rolling wavy lines, ответ инженера](https://ez.analog.com/video/f/q-a/12086/adv7441a-analog-video-rolling-wavy-lines)
  — помехи питания как возможный источник полос; не диагноз нашим записям.

| Вариант | Статус | Причина |
|---|---|---|
| NLMeans | Отложен, вне обязательной Phase 1 | CPU cost, без доказанного нужного выигрыша |
| atadenoise | Вне V1 | Temporal averaging рискует удалить короткое препятствие |
| BM3D | Вне V1 | Вычисления и настройка ради аккуратности denoise |
| av-denoise/NL4D | Возможный поздний backend | Дополнительные GPU/runtime/JIT зависимости |
| VapourSynth/Zsmooth/CNR4/CCD | Вне V1 | Интеграционная цена; сначала HQDN3D для chroma |
| Neural restoration | Вне V1 | Сложность; визуальное восстановление не цель |
| SDR/RF DSP | Вне обработки DVR | Работает с RF/IQ до записи |
| Av1an/chunk orchestration | Вне V1 | Не обоснован для начальных SD samples |
| Freeze вместо снега | Заменено вырезанием | Уточнение про паузы при замене батареи |
| Black/blue/frozen/NO SIGNAL screens | Позднее расширение | Требуются отдельные признаки и проверка |

Дополнение выборки 2026-10-04: пользователь предоставил `home-other-helmet`
с чередованием снега и синего экрана после отключения дрона и неподвижной
полезной сценой с мелким шумом пикселей. Возможность другого шлема не подтверждена.
Синий экран теперь проверяется отдельным ограниченным экспериментом;
это не автоматически принятая функция V1. Неподвижность или низкий temporal
MAD сами по себе не означают no-signal: полезную неподвижную сцену сохранять.
Разреженная проверка синего экрана пропустила краткие полезные вставки;
удаление всего кандидата отклонено. Нельзя считать успешный decode/PTS check
или преобладание однотонных кадров доказательством безопасного вырезания.
Наблюдения и измерения ведутся в [журнале](research/experiments-2026-10-04.md).

Каталог S2 и ссылки на av-denoise, Zsmooth, fpv-viewer-rs, fpv-drone-analog-rs,

## Эволюция и отменённые идеи

| Этап | Вклад в итог |
|---|---|
| S1: сколько весят пять минут | Проблема шума и связь битрейта/размера; численные оценки не гарантии |
| S2: готовые решения | Каталог кандидатов; широкий restoration pipeline позднее сокращён |
| S3: минимальный размер и простота | FFmpeg/HQDN3D/SVT, отказ от своего denoiser |
| S4: движение/препятствия и скорость | Осторожный temporal luma, отдельный benchmark, preset около 6 |
| S5: разные DVR и паузы между полётами | Auto idet, send_field, no-signal cut, самый узкий benchmark |

Не возвращать автоматически ранние идеи: film grain, настройку deinterlace
один раз под конкретный DVR, send_frame по умолчанию, обязательный широкий
перебор denoisers, замещение полного снега предыдущим кадром.
Проценты выигрыша из сторонних исследований и примеры MB/времени не являются
критериями приёмки. Формула размер ≈ длительность × битрейт / 8 описывает
оценку; аудио и контейнер добавляют объём.

## Текущий проект и продолжение после перезапуска

### Реализованный контракт ядра и начальные defaults

Уточнено и принято к реализации в текущем чате 2026-10-04: ядро — Python-пакет
`analog_fpv_compressor`, CLI — отдельный адаптер внутри того же проекта.
FFmpeg выполняет обработку пикселей и кодирование; NumPy используется для
метрик детектора. Общие dataclasses: `Settings`, `Analysis`, `Plan`, `Result`;
`analyze(settings)` → `build_plan(settings, analysis)` → `process(plan)`.
Callback получает `Event(code, data)`, `CancelToken` задаёт отмену.

Начальная версия политики `v1-research-defaults-1.0`: AV1 CRF 48, preset 6,
HQDN3D `3:5:1.5:6`, исходные размеры, film grain выключен. Это исходные
изменяемые defaults по первой выборке, не математический оптимум и не
подтверждение приемлемости потери деталей для всех пользователей.
Для ручного HEVC исходный CRF 32/preset medium; числа CRF разных codec
не эквивалентны качеству. Оба режима имеют ручные bitrate/CRF и preset.

Политика снега `snow-1.0` использует нативные timestamps и метрики на
160×120 с центральной 128×96 областью, пороги corr < .12, MAD > 25,
coarse_std/std < .55, std > 15. Подтверждение требует минимум 1 с наблюдаемых
кадров и 70% временной доли кандидатов. Короткие разрывы до .5 с объединяются
только без структурных кадров; при coarse_std/std ≥ .70 и std ≥ 15 кадр
сохраняется. Запас границ .25 с; подтверждённый хвост снега удаляется до EOF.
Пропуски кадров не считаются дополнительным доказательством снега.
Пороги откалиброваны на трёх файлах; blue removal выключен.

Auto idet: до трёх выборок по 150 кадров внутри сохраняемых участков,
не включая последующий снег. При минимум 50 классифицированных кадрах,
доле определённых ≥ 80% и преобладании progressive либо interlaced ≥ 80%
выбирается соответствующий режим; unknown сохраняет видео без bwdif
и сообщает неопределённость. Ручной on использует send_field, off пропускает idet.
Для interlaced дополнительно требуется согласованность TFF/BFF ≥ 80%:
противоречивая классификация полей не должна включать bwdif автоматически.

MKV и MP4 определяются расширением результата. `audio=keep`: FLAC в MKV,
AAC в MP4, общий сдвиг от границы исходного интервала, непрерывная выходная
шкала сэмплов. Отсутствующий звук не ошибка. Проверяется каждый output frame
относительно mapping, а не только число кадров/успешный decode.
План содержит явные интервалы; temporal-фильтры независимы на стыках.

Downscale пересчитывает SAR для сохранения отображаемых пропорций. Если во
входе SAR отсутствует, начальная политика предполагает квадратные пиксели
и фиксирует допущение в причине выбора; геометрия камеры по догадке не меняется.
При сохранении аудио MKV/FLAC может занимать больше исходного ADPCM-звука:
сохраняются декодированные сэмплы без потерь, а не исходные сжатые пакеты.
